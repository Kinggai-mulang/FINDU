# FINDU 0.8.1 验证记录

0.8.1 不增加功能，只做流畅度、代码结构与界面细节优化。引擎为 IPSPOS 提交 991fade（版本标识 BetaV0.611，GNSS Log=4 / StatusLog=1）。

## 环境

Windows 11 Pro，Intel Core Ultra 9 285K（24 线程），95 GB 内存，WebView2 156。对比对象为同一台机器上的 0.8.0 便携包与 0.8.1 构建，两者使用相同的 engine、product-runtime 目录。

## 性能对比

### 载入耗时的组成

两份 47 小时结果（`cargo run --release --bin load-check -- <a.log> <b.log>` 与上述桌面测量）：

| 环节 | 0.8.0 / 0.8.1 初版 | 现在 |
|---|---|---|
| Rust 解析两份 Log=4 | 4.5 s（逐个、每行一个 JSON 对象） | 0.54 s（并行、按列存放） |
| 编码 | JSON 0.6 s/份，共 368 MiB | 二进制 0.34 s，共 77 MiB |
| WebView2 传输与解析 | 约 7 s，其中一次 1.4 s 的 JSON 解析卡顿 | 传输约 0.65 s；解码约 1.3 s，分片执行 |
| 首屏分析（统计、事件、覆盖率） | 约 0.6 s | 约 0.35 s |

### 一致性

改动只涉及解析、传输与计算方式，结果数值不变：

- 新解析器与 0.8.1 初版解析器对上述两份日志的输出逐值比较：每份 14,229,156 个值完全一致（含键顺序）。
- 页面解码后的行与原 JSON 行逐值一致（`Object.is`，含 -0）；Rust 与 TypeScript 两端共用 `tests/fixtures/result-wire.*` 固定样例。
- 四种样本集合 × 两个时间窗的分析结果（统计、连续性事件、覆盖率、差分序列）序列化后与优化前逐字节相同。
- 诊断图的采样点与抽稀选点在 5 个字段（含对数、显示范围裁剪与缺口）共 169 万点上与优化前完全相同。

## 真实数据流

使用 `IPSPOS/Data/TEST/RTIET` 的 `Alloy-WHU.opt` 与 `Alloy-HC.opt` 同时实时运行约 3.5 分钟：

- 已读历元每秒加 1（145 秒内 5 → 150）。
- 每次增量读取 4–9 KB；0.8.0 每秒读取完整缓存，随运行时间增长到数 MB。
- 两路实时对比的时间窗每秒前进 1 秒，无页面错误。
- 全部停止后两路状态为 stopped。

结果传输改动后再次运行 `Alloy-WHU.opt` 90 秒：诊断行由 3 秒时的 1 行增至 89 秒时的 91 行，字段解码正常（74 列），停止后为 stopped，无页面错误。
